# CyberVPN Premium Smart RU
## Как должен работать VPN: полная схема маршрутизации, блокировок и пользовательского поведения

Версия документа: `1.0`
Профиль: `CyberVPN Premium Smart RU`
Основной клиентский шаблон: `cybervpn-premium-smart-ru-de-primary-hardened.yaml`
Платформа: Remnawave 2.8.0 + Mihomo / Clash Meta

---

# 1. Главная идея сервиса

Пользователь должен включить VPN **один раз** и больше не переключать локации вручную.

После подключения CyberVPN сам определяет, куда отправить каждый сайт, приложение или сетевое соединение:

```text
Обычный мировой интернет         -> Германия, 25 Gbit/s
Резервный европейский маршрут    -> Нидерланды, 10 Gbit/s
Российские сервисы               -> Москва или Санкт-Петербург, 25 Gbit/s
Заблокированные из РФ сервисы    -> Германия / Нидерланды
Реклама и трекеры                -> BLOCK / REJECT
Torrent                          -> BLOCK / REJECT
TOR                              -> best-effort BLOCK
Локальная домашняя сеть          -> DIRECT
```

Пользователь не должен выбирать отдельно:

```text
«Сейчас Германия»
«Теперь Россия»
«Теперь обратно Германия»
```

Вместо этого он подключается к одному профилю:

```text
CyberVPN Premium Smart RU
```

А маршрутизация выполняется автоматически на клиентском устройстве.

# 2. Серверная топология

## 2.1. Европейский контур

### Германия — основной маршрут

```text
Remnawave remark: 🇩🇪 DE Frankfurt 01 25G
Пропускная способность: до 25 Gbit/s
Роль: основной выход в интернет
```

Через Германию по умолчанию идут:

- обычные зарубежные сайты;
- YouTube;
- Discord;
- GitHub;
- OpenAI и другие AI-сервисы;
- Telegram и международные мессенджеры;
- стриминговые сервисы;
- весь трафик, который не совпал с RU-правилами или блокировками.

### Нидерланды — резервный маршрут

```text
Remnawave remark: 🇳🇱 NL Amsterdam 01 10G
Пропускная способность: до 10 Gbit/s
Роль: резервный EU-контур и ручной запасной маршрут
```

Нидерланды используются:

- если Германия недоступна;
- если у отдельного пользователя или сервиса маршрут через NL работает лучше;
- для ручного переключения в клиенте;
- как запасной европейский выход.

## 2.2. Российский контур

### Москва

```text
Remnawave remark: 🇷🇺 RU Moscow 01 25G
Пропускная способность: до 25 Gbit/s
Роль: российский IP для RU-сервисов
```

Пользователь не выбирает город вручную. Группа `⚡ RU Auto` выбирает доступную или наиболее подходящую RU-ноду.

# 4. Общая схема движения трафика

```text
Пользовательское устройство
          |
          v
Mihomo TUN / DNS hijack / Sniffer
          |
          v
Проверка правил сверху вниз
          |
          +--> Локальная сеть? -----------------> DIRECT
          |
          +--> Реклама / трекер? ---------------> REJECT
          |
          +--> Torrent? ------------------------> REJECT
          |
          +--> TOR? ----------------------------> BLOCK
          |
          +--> YouTube / Discord / AI / GitHub? -> EU / DE
          |
          +--> Заблокировано или нестабильно РФ? -> EU / DE
          |
          +--> Российский сервис? --------------> RU Moscow / RU SPB
          |
          +--> Всё остальное -------------------> DE 25G
```

# 5. Порядок обработки правил

Mihomo применяет правила **сверху вниз**.

Как только найдено первое подходящее правило, дальнейшая проверка прекращается.

Правильный порядок:

```text
1. DNS hijack
2. Локальные и частные сети
3. Защита от IPv6 leakage
4. Исключения для служебных VPN/remote-control приложений
5. Реклама и трекеры
6. Windows telemetry
7. QUIC / DoQ policy
8. Проверка внешнего IP
9. Torrent
10. TOR
11. Игры и системные сервисы
12. YouTube
13. Discord
14. Telegram и мессенджеры
15. AI-сервисы
16. GitHub и Dev-сервисы
17. Сайты, которые нельзя отправлять через РФ
18. Российские сервисы
19. Финальный MATCH -> EU / DE
```

Такой порядок нужен, чтобы широкое правило `.ru -> Россия` не перехватывало сайты, которые должны идти через Европу.

# 8. Исключения: какие русскоязычные сайты нельзя отправлять через РФ

Некоторые сайты имеют русскую тематику или `.ru`-подобный домен, но могут быть заблокированы или нестабильны из РФ.

Они должны проверяться **до** широких RU-правил и отправляться через EU.

Примеры:

```text
habr.com
4pda.to
meduza.io
theins.ru
novayagazeta.eu
mediazona.online
currenttime.tv
svoboda.org
archive.org
proton.me
protonmail.com
```

Также через EU идут rule-set категории:

```text
ru-eu-exceptions
ru-inside
ru-bundle
refilter_domains
refilter_ipsum
rknasnblock
```

Схема:

```text
Сначала проверить EU-исключения.
Только потом применять широкие RU-правила.
```

Иначе `.ru` правило может отправить заблокированный ресурс обратно через российскую ноду.

# 14. Блокировка рекламы

В шаблоне используются несколько источников блокировки:

```text
oisd_big
category-ads-all
win-spy
```

## 14.1. Что блокируется

- рекламные домены;
- рекламные CDN;
- tracking pixels;
- рекламная аналитика;
- часть мобильных SDK трекинга;
- часть Windows telemetry;
- известные домены сбора данных.

## 14.2. Два уровня блокировки

### DNS-уровень

Для известных рекламных доменов DNS отвечает:

```text
rcode://name_error
```

Это означает, что рекламный домен не получает IP и не загружается.

### Routing-уровень

Если домен всё же был разрешён или приложение использует прямой IP:

```text
RULE-SET -> REJECT
```

Соединение отклоняется.

## 14.3. Пользовательский эффект

```text
меньше рекламных баннеров
меньше фоновых запросов
меньше трекеров
меньше расход трафика
быстрее загрузка некоторых страниц
```

## 14.4. Ограничения

Нельзя обещать:

```text
100% блокировку всей рекламы
полное удаление рекламы во всех приложениях
гарантированное удаление всей рекламы YouTube
```

Корректная формулировка:

```text
Блокировка известных рекламных доменов и трекеров
```

# 15. Защита от трекеров

Трекеры блокируются теми же rule-set списками, что и реклама.

Система пытается остановить соединение до того, как данные уйдут на tracking endpoint.

Блокируются или ограничиваются:

```text
поведенческая аналитика
рекламные идентификаторы
tracking pixels
часть cross-site tracking
часть телеметрии приложений
часть Windows telemetry
```

Это не делает пользователя полностью анонимным, но уменьшает количество известных отслеживающих запросов.

# 16. Безопасный DNS

Шаблон использует:

```text
DNS hijack
Fake-IP
DoH
nameserver-policy
DNS через выбранную proxy-group
```

## 16.1. DNS hijack

Все запросы на порт 53 перехватываются Mihomo:

```yaml
- DST-PORT,53,DNS-OUT
```

Это мешает приложениям обходить заданную DNS-политику через обычный системный DNS.

## 16.2. Fake-IP

Mihomo выдаёт приложению временный fake IP, сохраняет связь:

```text
fake IP <-> настоящий домен
```

Благодаря этому правило может применяться именно по доменному имени, даже если приложение дальше работает с IP.

## 16.3. Раздельный DNS для RU и EU

RU-сервисы резолвятся через RU-контур:

```text
ru-services-inline
geosite-ru
-> DNS через 🇷🇺 RU Sites
```

Глобальные и заблокированные сервисы резолвятся через EU:

```text
YouTube
Discord
Telegram
AI
GitHub
ru-bundle
refilter
-> DNS через 🌍 World / EU
```

Это помогает получить правильные CDN/geo-ответы для нужного региона.

# 17. TUN и Sniffer

## 17.1. TUN

TUN-режим перехватывает системный трафик, поэтому правила работают не только в браузере, но и в приложениях.

Основные настройки:

```text
auto-route
strict-route
auto-detect-interface
dns-hijack
```

## 17.2. Sniffer

Sniffer определяет домен по:

```text
HTTP Host
TLS SNI
QUIC metadata
```

Это нужно, когда приложение подключается сразу к IP, но внутри TLS/HTTP всё равно содержит имя домена.

# 19. QUIC и DoQ

В hardened-профиле QUIC/DoQ могут блокироваться или ограничиваться:

```text
UDP 443
UDP 853
```

Цель:

- заставить часть сервисов перейти на обычный TCP/TLS;
- улучшить предсказуемость SNI/sniffing;
- уменьшить обход DNS-политики через DoQ;
- повысить стабильность на проблемных сетях.

Побочный эффект:

- некоторые приложения могут потерять HTTP/3;
- задержка может немного увеличиться;
- если конкретный сервис ломается, QUIC-policy нужно тестировать отдельно.

# 20. Torrent

Torrent должен быть запрещён в несколько слоёв.

## 20.1. Клиентский слой

В Mihomo:

```text
torrent clients
tracker domains
torrent websites
process names
-> 🧲 Torrents
-> REJECT
```

Группа `🧲 Torrents` в публичном hardened-профиле должна быть:

```text
REJECT-only
```

Пользователь не должен иметь переключатель `DIRECT` или `Proxy` для torrent.

## 20.2. Серверный слой

Remnawave Node Plugin:

```text
torrentBlocker.enabled = true
```

При обнаружении BitTorrent:

```text
Xray / Node detects traffic
-> создаётся report
-> IP пользователя блокируется nftables
-> соединения сбрасываются
```

## 20.3. Backend abuse policy

CyberVPN backend должен принимать:

```text
torrent_blocker.report
```

И выполнять:

```text
логирование
уведомление администратора
подсчёт повторных нарушений
опциональное отключение пользователя
```

Важно: Torrent Blocker не является абсолютной DPI-системой, поэтому клиентская блокировка и серверный plugin должны работать вместе.

# 21. TOR

TOR блокируется в режиме best-effort.

Клиентский шаблон блокирует:

```text
.onion
torproject.org
tor2web
Tor Browser process
obfs4proxy
snowflake-client
```

Маршрут:

```text
TOR -> ⛔ BLOCK -> REJECT
```

Серверный Egress Filter может дополнительно использовать:

```text
ext:tor-exit-nodes
ext:tor-relays
```

Но эти списки должны регулярно обновляться.

Без актуального updater нельзя обещать полную блокировку TOR, поскольку bridges и obfuscation могут работать через обычный HTTPS.

# 22. VLESS RAW/TCP и XHTTP

Маршрутизация и транспорт — это разные уровни.

## 22.1. Два варианта подключения к каждой ноде

На каждой ноде должны быть:

```text
VLESS Reality RAW/TCP 443
VLESS Reality XHTTP 8443
```

Итого:

```text
DE RAW/TCP 443
DE XHTTP 8443
NL RAW/TCP 443
NL XHTTP 8443
Moscow RAW/TCP 443
Moscow XHTTP 8443
SPB RAW/TCP 443
SPB XHTTP 8443
```

## 22.2. Что выбирает транспорт

Транспорт определяет, **как клиент подключается к конкретной ноде**.

Маршрутизация определяет, **через какую ноду отправить конкретный сервис**.

Пример:

```text
Пользователь подключён к DE через XHTTP.
Открывает Госуслуги.
Mihomo создаёт отдельное соединение к RU-нODE.
Это RU-соединение может использовать RAW/TCP или XHTTP,
в зависимости от доступных proxy entries и выбранной группы.
```

## 22.3. Обязательное требование

Работающий XHTTP не должен скрывать поломанный RAW/TCP.

VPN Tester должен отдельно проверять:

```text
4 VLESS Reality RAW/TCP proxy
4 VLESS Reality XHTTP proxy
```

# 23. Failover и отказоустойчивость

## 23.1. Если DE недоступен

Должен быть доступен резерв:

```text
NL Auto
```

В зависимости от выбранной структуры группы пользователь или fallback-группа переключается на NL.

## 23.2. Если Moscow недоступен

```text
RU Auto -> SPB
```

## 23.3. Если SPB недоступен

```text
RU Auto -> Moscow
```

## 23.4. Если обе RU-ноды недоступны

В группе `🇷🇺 RU Sites` может быть аварийный fallback:

```text
🌍 World / EU
```

Но в таком случае российский сервис увидит EU IP и может работать ограниченно.

Это лучше, чем полностью оборвать интернет, но должно отображаться в мониторинге как degraded state.

# 26. Как должна работать проверка IP

Проверочные сервисы:

```text
ipwho.is
ipinfo.io
api.ip.sb
ifconfig.me
2ip.io
```

должны специально отправляться через:

```text
🌍 World / EU
```

Чтобы пользователь при обычной проверке видел основной EU IP, а не RU IP, который используется только для RU-сервисов.

Пример:

```text
2ip.io -> DE IP
Ozon   -> RU IP
```

Это нормальное и ожидаемое поведение Smart Routing.

# 27. Учёт трафика и Unlimited

Даже если тариф отображается как:

```text
Unlimited / fair use
```

Remnawave должен продолжать считать:

```text
usedTrafficBytes
lifetimeUsedTrafficBytes
onlineAt
node usage
```

Клиенты HAPP/INCY должны получать заголовок:

```text
subscription-userinfo
```

Он нужен для отображения:

```text
использованного трафика
срока подписки
общего лимита или Unlimited-состояния
```

Unlimited означает отсутствие жёсткого пользовательского лимита, а не отключение статистики.

# 28. Что нельзя делать

Нельзя строить схему:

```text
Пользователь -> RU-нода -> DE-нода -> интернет
```

Для всего трафика.

Даже при быстрых RU-нODE это создаёт:

```text
лишний hop
лишнюю задержку
двойную нагрузку
сложность диагностики
единую точку отказа
```

Правильная схема:

```text
Пользовательский клиент сам открывает отдельные соединения:

EU-сервис -> непосредственно DE/NL proxy
RU-сервис -> непосредственно Moscow/SPB proxy
```

Это client-side rule-based split routing.

# 29. Порядок внедрения

```text
1. Remnawave Config Profile содержит RAW/TCP 443 и XHTTP 8443.
2. Оба inbound активированы на всех 4 нодах.
3. Для каждого inbound создан отдельный Host.
4. Internal Squad содержит оба inbound.
5. Пользователь premium_smart_ru получает Internal Squad.
6. Пользователь получает External Squad с MIHOMO template override.
7. Remnawave отдаёт generated Mihomo YAML с 8 proxy entries.
8. Mihomo загружает rule-providers.
9. Default группа выбирает DE.
10. RU Sites выбирает RU Auto.
11. Блокировки работают до routing rules.
12. Torrent/TOR дополнительно контролируются Node Plugin.
13. VPN Tester проверяет RAW/TCP и XHTTP отдельно.
14. Runtime smoke подтверждает реальные exit countries.
```
